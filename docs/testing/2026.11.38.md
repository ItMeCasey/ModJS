# Testing 2026.11.38 (villager trades)

Branch `villagers`. All ten builds carry the version bump.

## Done and seen

- All ten builds compile. Unit tests (`TradesTest`, 12 tests): trade parsing and defaults, validation messages that name the field, operation bookkeeping (script reloads drop a type's operations, client scripts cannot change trades), the generated 26.x files (trade file, replacing tag that keeps the original entries, replace, clear, remove by object and function, wandering trader pool names, other namespaces, the spelling of each 26.x build).
- Headless self test, failures=0 on all ten builds (Forge and NeoForge 1.20.1, 1.21.1, 26.1.2, 26.2, 26.3): a villager is created, its level 1 trades read, and checked: `replaceTrades` leaves a cleric exactly the two new trades (costs, counts, max uses, xp); `removeTrades` of everything plus `addTrade` leave a toolsmith one trade; villager type conditions offer a desert villager only the desert trade and a plains villager only the plains trade; `clearTrades` leaves a librarian without trades; a trade with a biome condition loads (the data is valid on every 26.x build).

## Findings

- 26.x: the data files differ between builds: 26.3 spells loot conditions `type` and `minecraft:predicates`, 26.2 `condition` and `minecraft:predicates`, 26.1.2 `condition` and `predicates`; the generator follows the build.
- 26.x: a trade set reads a tag that may name other tags (`#minecraft:common_smith/level_1`), so the original pool is read through those tags; otherwise shared trades could not be removed.
- 1.21.1: the game keeps the trades of the experimental trade rebalance in their own lists, which no loader event reaches, and the headless test world has that feature on. ModJS changes those lists too when the server starts.
- 1.20.1 and 1.21.1: a filter judges existing trades by the offer they make with no villager, which fails for listings that need a villager; a filter with no conditions (`{ give: '*' }`) removes those too. 1.20.1 picks the villager's trades once and does not draw again when a trade is skipped, so a pool with conditions can give fewer trades there.

## Not done

- Custom professions (`Villagers.profession`): not built. See the report: each loader needs its own registration of a profession and a job site POI, and villager skins; none of that exists in ModJS yet.
- Real client and real villagers (a village, level ups, restock, the trading screen).
- Other mods' professions on 26.x only work when their trade tags follow the `<profession>/level_N` naming.
